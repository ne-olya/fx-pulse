# Замороженный UZS-сигнал на произвольную дату

Дата проверки: **6 сентября 2026 года**. Статус: **код интеграции готов, официальный артефакт для включения в основной CLI отсутствует**.

## Что именно сделано

В реестр `fxpulse.indicators` добавлен индикатор `uzs_frozen_consensus`. Он читает компактный исторический replay официального UZS-кандидата, проверяет SHA-256 по manifest и возвращает решение только для запрошенной даты и только после указанного `available_at`.

Replay выбран намеренно. Победитель — не один CatBoost, обученный один раз на всей истории. Для каждого OOT-года использовались свои модели:

```text
последние четыре года train
        ↓
purge пяти необозримых меток
        ↓
отдельный OOT-год
        ↓
UZS-score + четыре confirmation-score
        ↓
causal percentile по прошлым 60 score
        ↓
consensus + cooldown + максимум два сигнала в неделю
```

Если сохранить один `.cbm`, обученный до сентября 2026 года, и применить его к дате 2022 года, получится заглядывание вперёд. Replay сохраняет именно то решение, которое выдала соответствующая past-only модель в своём годовом fold. Поэтому для исторической демонстрации это корректнее одного общего файла модели.

Код также получил две дополнительные защиты:

- `load_panel` передаёт индикатору точный `as_of`, идентификатор ряда и путь к источнику;
- `signals_as_of` не переиспользует старый последний курс после остановки источника: по умолчанию ряд старше семи дней считается несвежим, и результат пустой.

## Почему индикатор пока не включён в основной `configs/grid.json`

В Git отсутствуют три игнорируемых результата финального прогона:

```text
artifacts/uzs_final_experiment_20260905/policy_scores.csv.gz
artifacts/uzs_final_experiment_20260905/signals.csv.gz
data/processed/gdelt_news_daily_features.csv
```

Нет и исходного `artifacts/uzs_final_features_20260905/features.csv.gz`, однако его табличное содержимое удалось восстановить: три локальные копии `uzs_feature_enrichment_v2*` имеют один и тот же SHA-256 распакованного CSV. Блокирующим входом остаётся прежде всего исторический снимок GDELT либо уже рассчитанные `policy_scores/signals`.

Попытка повторно скачать GDELT была сделана штатным зарегистрированным загрузчиком. Origin многократно ответил `HTTP 429`, зарегистрированный Jina fallback — `451`, дополнительный read-only CORS fallback — `522/401`. Подменять новости нулями или брать даты другой 255-сигнальной UZS-модели нельзя: это изменит официальный кандидат со 140 сильными сигналами.

Поэтому основной grid оставлен рабочим. Готовая opt-in запись лежит в `configs/frozen_uzs_indicator.json` и станет активной после появления проверенного replay.

## Как завершить интеграцию после восстановления артефакта

Если каталог финального прогона восстановлен, одна команда создаёт replay, его manifest и даты для графика:

```bash
uv run python -m fxpulse.frozen_uzs_replay
```

Экспортёр не доверяет файлам на слово. Он пересчитывает итоговые метрики и завершится ошибкой, если не совпадут опубликованные контрольные значения:

- 140 сильных сигналов;
- raw lift около 1,56;
- same-week lift около 1,25;
- частота около 0,61 сигнала в неделю.

После успешной проверки:

```bash
uv run python -m fxpulse.signal_cli \
  --grid configs/frozen_uzs_indicator.json \
  --date 2026-06-10
```

Затем opt-in запись можно перенести в основной `configs/grid.json`. До этого шага команда с frozen grid ожидаемо не является рабочей поставкой: нужного файла модели нет.

## Тесты контракта

Добавлены автоматические проверки:

- дописывание будущих CBR-строк не меняет исторический ответ frozen-индикатора;
- дата далеко за концом истории возвращает пустой результат, а не сигнал на устаревшем курсе;
- manifest и replay сверяются по SHA-256;
- strength обязан лежать в `[0, 1]`;
- replay обязан содержать не более одной строки на дату.

Существующий тест на 50 исторических срезах остаётся неизменным и проходит.

## Что нельзя утверждать

Replay — это способ честно воспроизвести исторические OOT-решения. Он не является live-инференсом и не делает кандидата production-ready. Для новых дат нужен сервис point-in-time признаков, ежегодного или более частого retraining, сохранения score-history и проверки банковского исполнимого курса.
