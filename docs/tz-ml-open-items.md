# Задача 1. Продуктовый сигнал на произвольную дату среза

## Зачем

Постановка, «Ожидаемый результат», пункт 1:

> «Обязателен расчёт сигналов на произвольную дату среза, иначе решение невозможно проверить на отсутствие заглядывания вперёд».

И отдельно: **«Дисквалифицирующее условие: любое заглядывание вперёд»**.

Сейчас `signals_as_of` и `signal_cli` считают только базовые индикаторы из `configs/grid.json`. Замороженный CatBoost-кандидат через эту точку не проходит. Проверка идёт по библиотеке правил, которую мы сами отвергли, а продуктовый сигнал ей не покрыт.

## Что сделать

Зарегистрировать замороженную модель как индикатор в существующем реестре `src/fxpulse/indicators/`, чтобы `signals_as_of` возвращала её в общей таблице.

### Контракт

Менять не нужно, он подходит:

```python
@indicator("uzs_frozen_consensus")
def uzs_frozen_consensus(panel, *, model_path, lookback=60, top_share=0.2, min_history=20):
    """panel уже обрезан по as_of — на вход попадают только известные наблюдения."""
    return IndicatorOut(
        fired=bool(percentile >= 1 - top_share),
        strength=float(percentile),                    # обязано быть в [0, 1]
        details={"direction": "favorable", "consensus": float(percentile)},
    )
```

`direction`, `speed`, `scenario` задаются в `configs/grid.json` рядом с остальными:

```json
{"name": "uzs_frozen_consensus",
 "params": {"model_path": "models/uzs_frozen.cbm"},
 "direction": "favorable", "speed": "slow", "days_to_confirm": null, "scenario": "T1"}
```

### Развилка: consensus считается по пяти коридорам

Индикатор получает панель одного коридора, а модели нужны пять.

| Вариант | Что делать | Рекомендация |
|---|---|---|
| **A** | Индикатор сам подтягивает остальные коридоры через `load_panel(series_id, raw_dir, as_of=T)` | **Берём это.** Контракт не меняется, границу `as_of` режет тот же код, что и везде. Лишний I/O — приемлемая цена за нулевой риск утечки |
| Б | Расширить `Config`, чтобы индикатор получал сразу все панели | Только если вариант A окажется слишком медленным. Меняет контракт и требует новых тестов на границу |

### Артефакты модели

`artifacts/` в `.gitignore`, а модель нужна при каждом вызове CLI. Два выхода, **решение за вами**:

- положить файл модели в репозиторий (например `models/uzs_frozen.cbm`) и снять его из игнора;
- переобучать детерминированно из конфига при первом вызове с кэшем на диск.

Первое проще и быстрее; второе честнее по воспроизводимости. Если файл маленький — берите первое.

## Критерии приёмки

1. `uv run python -m fxpulse.signal_cli --date 2026-06-10` печатает таблицу, **в которой есть строка с индикатором модели**, а не только базовые.
2. Та же команда на дате за концом истории возвращает **пустую таблицу без исключения**.
3. Тест: для даты `T` результат индикатора не меняется, если в сырые данные дописать наблюдения после `T`. Это прямая проверка дисквалифицирующего условия.
4. Существующие 50 срезов против заглядывания вперёд проходят по-прежнему.
5. Строка запуска добавлена в README, в раздел «Запуск».

**Оценка:** полдня.

# Задача 2. Матрица «индикатор × коридор × метрики»

## Зачем

Постановка, «Ожидаемый результат», пункт 2:

> «Отчёт по бэктесту. Матрица "индикатор × коридор × метрики" с прямым выводом о том, какие индикаторы информативны, а какие следует исключить и почему».

Наш слайд 2 — это матрица «коридор × метрики», она отвечает на вопрос «какой коридор пилотировать». Пункт 2 требует другого: по строкам **индикаторы**, и вывод, какие из них выбросить. Это отчётный документ, не слайд.

## Что сделать

Прогнать сетку индикаторов из `configs/grid.json` через существующий бэктест **на пяти коридорах кейса** и свести результат в одну таблицу.

Сейчас базовые индикаторы мерились на `MOEX:CNYRUB_TOM`, а не на UZS, TJS, KGS, AMD и KZT. Это и есть недостающая часть.

### Форма результата

По строкам индикаторы, по столбцам коридоры, в ячейке два числа — **строгий lift и сигналов в неделю**. Справа вердикт с причиной.

| Индикатор | UZS | TJS | KGS | AMD | KZT | Вердикт |
|---|---|---|---|---|---|---|
| Уровень: нижние проценты диапазона | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| Моментум: N дней подряд вниз | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| Разворот вверх от минимума | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| Сезонность и праздники | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| Волатильность и режим | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| **Скор модели с consensus** | **1,25 / 0,61** | 1,24 / 1,14 | 1,20 / 1,11 | 1,24 / 1,11 | 1,13 / 1,11 | **оставить** |

Нижняя строка уже посчитана, она из `O_final-corridor-matrix.md`. Остальные — то, что нужно получить.

### Требования к прогону

- Горизонт `h = 5` торговых дней, как у основного кандидата, чтобы строки были сравнимы.
- Метрики те же, что в матрице коридоров: hit rate, raw lift, same-week lift, сигналов в неделю.
- Период и метка совпадают с матрицей коридоров.
- Параметры индикаторов не подбираются под результат: берётся сетка из конфига как есть.

### Вердикты

По каждой строке — одна фраза с причиной: «исключить, lift ниже 1,0 на четырёх коридорах из пяти», «исключить, выгода отрицательная», «оставить как содержание сообщения, но не как триггер».

**Это стоит сделать, даже зная ответ заранее.** Постановка отдельно оговаривает: «Отдельно ценим честный отрицательный результат: "индикатор X на коридоре Y не отличим от случайного дня" — полезный итог, **если он доказан методически чисто**». Сейчас мы этот вывод произносим, но на коридорах кейса не доказали.

## Критерии приёмки

1. Файл `docs/indicator-corridor-matrix.md` с заполненной таблицей.
2. Машиночитаемая версия рядом: CSV или JSON с теми же числами.
3. По каждой строке есть вердикт с причиной, а не только числа.
4. Прогон воспроизводится одной командой, команда указана в документе.

**Оценка:** полдня, считается одним прогоном.

# Задача 3. Выгрузка дат срабатывания для графика

## Зачем

Постановка, пункт 9: «график курса по коридору **с отметками срабатываний** и сквозной сценарий».

График встроен в демонстрацию — [прототип](prototype/transfer-flow.html), блок над телефоном. Кривая построена на реальных курсах ЦБ за последний год. **Отметок нет: массив `SIGNALS` в коде пуст**, потому что дат срабатывания у продакта нет — `artifacts/` не в репозитории.

## Что сделать

Выгрузить даты срабатывания замороженного UZS-кандидата за последние 12 месяцев.

```text
docs/prototype/signals-uzs.csv

date,corridor
2025-10-14,RUB->UZS
2025-11-03,RUB->UZS
...
```

Одна строка на принятый сигнал — уже после causal-порога, cooldown и недельного лимита, то есть ровно те дни, когда клиент получил бы пуш.

## Критерии приёмки

1. Файл в репозитории, даты в ISO.
2. Число строк совпадает с частотой из матрицы: около 0,61 в неделю, то есть **примерно 30 за год**.
3. Все даты попадают в диапазон 02.09.2025 — 02.09.2026, иначе не отрисуются.

**Оценка:** 15 минут. Подставлю в прототип сам.
